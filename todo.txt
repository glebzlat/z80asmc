Fix the bug with incorrect token's column calculation. E.g. the string
"0x31415\0" is expected to produce the following sequence of tokens:

- {.value = "31415", .len = 5, .type = TOKEN_HEXADECIMAL, .line = 1, .col = 0}
- {.value = "", .len = 0, .type = TOKEN_END, .line = 1, .col = 7}

Instead the first token that it actually produces is:

- {.value = "31415", .len = 5, .type = TOKEN_HEXADECIMAL, .line = 1, .col = 7}

The bug lies in that the lex's BoL (beginning of the line) is subtracted from
the current index. The correct implementation would be to subtract the sum of
BoL and given token's symlen from the current: col = cur - (symlen + BoL).

Fix strncasecmp NUL-terminator handling. The loop does not stop when one of
the strings runs into a NUL byte: it only returns 0 when both strings are
NUL at the same position. If only one is NUL, the function falls through to
the magnitude comparison and returns -1 or 1, which is incorrect by both
POSIX strncasecmp and C standard strncmp semantics. Both should return 0
when one string runs out before the other and the chars matched up to that
point. Affects callers that pass strings shorter than `len`.
